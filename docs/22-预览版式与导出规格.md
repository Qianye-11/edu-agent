# 22 · 预览版式与「预览即导出」规格（v1.16.0）

> **这份文档是什么**：老师反馈「预览里的 PPT 不好看」之后，把「改成什么样、按什么数值、怎么算改好了」一次性定死的**规格书**。
> **怎么用**：§1 是**已经拍板的结论**（不用再讨论方案）；§3 的数值是**唯一权威**（代码、测试、其它文档都从它来）；§8 是排期。
> **相关**：`docs/19-PPT优化与幻灯片编辑.md`（实施与验收）、`docs/14-会话内文档预览.md`（面板与四页签）、`docs/08`（本机 WPS / Office 现状）。
> **出处**统一收在 §11，正文只引编号（如 `[S1]`）。

## 0. 一页看懂（给非技术读者）

**现在为什么难看**（三条，都能对上代码）

1. 预览台是一整块**深蓝底 + 白字**（`.dp-stage` 用 `#0f172a` 铺满），字号只有两档（标题 17px、正文 12.5px）——它看起来像**开发调试页**，不像一张要给全班看的幻灯片；
2. 每一页都是「一个标题 + 一串小圆点」，最多六条并列，没有留白、没有版式变化——这是"土味 PPT"最常见的来源；
3. 预览（浏览器 HTML）和下载出来的 pptx（服务端 python-pptx `pptx_native`）是**两套各写各的坐标**，所以"预览里看到的"和"下载后打开的"从来不一样；中文还可能掉成宋体。

**这次改成什么**（四条）

1. 用一份**数值表（tokens）**统管版面：画布 1280×720、安全边距、字号阶梯、配色占比、线宽圆角。表只有一份。
2. 幻灯片改由**同一个源（SVG）**同时产出预览和 pptx：预览就是这份 SVG 直接显示；导出就是把同一份 SVG 交给本地转换器，变成"能改字的原生 pptx"。
3. 版式从"一页六个圆点"改成 **6 种带槽位的版式**（封面 / 章节 / 要点 / 两栏 / 图文 / 结尾），内容密度超了就提示拆页（**不截断**）。
4. 加一个自动检查（用本机 Edge 无头浏览器）：量**宽高比 / 空白 / 元素碰撞 / 左右失衡**四个指标，先记录今天的数值（基线），再要求"不变差且达标"；检查项和阈值照抄别人已经跑通的清单（内容溢出、底部空太多、标题贴太近、版式不在白名单里，都算不合格），版式也**锁定**成 6 种，不能临时乱排 [S11]。

**你会看到的变化**

| | 现在 | 改完 |
|---|---|---|
| 预览台底色 | 满屏深蓝 + 白字 | 白 / 纸白（浅色主题），只有细线和关键词用主色 |
| 字号 | 17px / 12.5px 两档 | 封面 72 / 页标题 44 / 正文 24 / 注释 15（画布 px，四档） |
| 一页内容 | ≤6 条圆点 | ≤5 个模块、每模块 ≤22 字，超出提示拆页 |
| 预览 vs 下载 | 两套渲染，可能不一样 | 同一个 SVG 源，所见即所得 |
| 中文字体 | 可能掉宋体 | 只用本机已装字体（微软雅黑 / Noto Sans SC），并有单测校验 |

**不用你懂的词**：tokens、槽位、SVG、无头浏览器 —— 见 §10 词汇表。

## 2. 路线对比：为什么选 D

三条路线的差别不在"哪个渲染得更好看"，而在**"源"是什么**——源决定预览与导出能不能是同一份东西。

| 维度 | A. HTML + tokens + pptxgenjs 母版 | B. HTML → 原生 pptx（转换流水线） | **D. SVG 单源（选定）** |
|---|---|---|---|
| 预览与导出是否同源 | ❌ 两套渲染，只共享数值 | ✅ 同一份 HTML | ✅ **同一份 SVG** |
| 需要新装什么 | 不用 | `playwright`（**核心依赖**，不是只审计要）[S4]；可驱动已装的 Edge，**不必**下 Chromium；要字体正确还得把字体装进系统目录 [S4] | 不用（`svg_to_pptx.py` 已在 `.deps/ppt-master`） |
| 文字是否原生可编辑 | ✅ | ✅ 矢量优先，装饰走截图兜底 [S4] | ✅ 原生 DrawingML 文本 |
| 版式数值从哪来 | 自写 | 自写 | **直接取上游 style-system** [S1–S3]，上游就是给 SVG 管线写的 [S7] |
| 与本项目已有资产 | 复用现有面板代码 | 全新链路 | 与 `pptx_to_svg.py --roundtrip`（导入旧稿→改）**同源闭环** |
| 与"页签内编辑"计划（docs/19 §8–§12） | 兼容 | ⚠️ 冲突：转换后是"位置"不是"槽位" | ✅ 兼容：编辑槽位 → 重生成 SVG |
| 离线确定性 | ✅ | ⚠️ 依赖浏览器渲染，字体/版本会飘 | ✅ 纯本地脚本 |
| 主要风险 | "预览 ≠ 导出"永远修不掉 | 装依赖 + 字体安装 + 不承诺 1:1 [S4] | 要写"槽位 → SVG"这一小段生成器（§6.1） |
| 结论 | 保留为**回退**与"文档页签"渲染 | 只在"HTML 必须唯一源"时才考虑 | **选定** |

两条**必须纠正的旧说法**（原文有误）：

1. ❌「PptxGenJS 母版能改善我们的导出」——我们的浏览器 deck **只在内存里建模型、从不落盘**（`docpBuildDeck` 注释：*绝不 writeFile*），真正的下载走服务端 `pptx_native`。所以 `defineSlideMaster` [S5] 对**当前导出路径无直接作用**，只在"以后改用 pptxgenjs 出文件"时才相关；
2. ❌「路线 B 只有审计需要渲染器」——`html-to-editable-pptx` 的 `requirements.txt` 把 `playwright>=1.40` 放在 **Core conversion pipeline**，可选审计那块才是 `pdf2image` / `pywin32`；它还带 `scripts/measure.py`(64KB) 与 `tests/test_measure_browser.py` ⇒ **转换本身就要真浏览器** [S4]。

## 2A. 两份现成 skill 的实读结论（2026-09-25 补）

### ppt-master（[hugohe3/ppt-master](https://github.com/hugohe3/ppt-master)）—— 我们已经在用的那一个

- **是什么**：一套跑在 AI 工具里的**工作流包**（不是库）。它的中间源是 SVG，`svg_to_pptx.py` 把 `svg_output/*.svg` 转成**直接可编辑的原生 DrawingML**：母版 / 版式继承、原生形状与连接符、数据驱动的图表与表格、原生公式、备注与旁白、转场动画 [S10]。三条顶层路线：从材料生成新 deck / 从参考资料提炼模板（品牌·风格·版式·成品）/ 改你已有的 `.pptx`（含只加备注与动画）。
- **许可与版本**：**MIT**；本项目按 commit **`481e057e`**（2026-09-23）验证，**与核对时的上游 `main` HEAD 一致**（D12）。
- **我们只"外部调用"这几个脚本**（不 import 它的包、**不改它的文件** —— 它启动时有 `require_skill_integrity()` 完整性校验，改了直接拒绝运行）：

| 脚本 | 我们用它做什么 | 状态 |
|---|---|---|
| `svg_quality_checker.py --canonical-authoring --stage final --quick-generate --json` | 出"最终质量报告"（`--quick-generate` 免 `spec_lock.md` 的前提条件） | ✅ 已用在样张链路 |
| `svg_to_pptx.py <project> --quick-generate -o out.pptx` | SVG → 原生可编辑 pptx（§6） | ✅ 已用在样张链路 |
| `pptx_intake.py` / `beautify_inventory.py` | 读别人的稿：体检、逐页台账、`--verify` 内容零丢失校验 | ✅ v1.15.0 已用 |
| `pptx_to_svg.py <pptx> --roundtrip` | （二期）导入旧稿 → 改成我们的版式再导出 | ⏳ 未接 |

- **踩过的工程约束**（写下来省得再踩）：
  1. 项目工作区形状是 `<project>/svg_output/*.svg`，导出会去读 `<project>/validation/` 里的质量报告；
  2. 产品 status 是 `passed-with-warnings` 时 **CLI 退出码仍是 1** ⇒ 判定要看报告里的 `status`，**不能只看退出码**；
  3. 画布由 SVG 根的 `viewBox` 决定（我们写 `0 0 1280 720` → 16:9），尺寸/边距它不替你算；
  4. 纯西文的 run 会被写上 `<a:ea typeface="Arial">`（无害）；含中文的 run 才会点名字体 ⇒ §6.2 的字体检查必须**按 run 逐条核**，不能只看"包里有几个 typeface"。

### guizang-ppt-skill（[op7418/guizang-ppt-skill](https://github.com/op7418/guizang-ppt-skill)）—— HTML 网页 PPT：两套视觉系统 + 自带校验脚本

- **是什么**：给 Claude Code / Codex 用的 skill，产出**单文件 HTML 横向翻页 PPT**（自带演讲者模式、`motion` 运行时、按 `B` 关动画的低性能静态模式），并附带"生成配图 / 多平台封面"的流程。作者是歸藏（op7418），内容来自他若干线下分享的沉淀 [S11]。
- **两套视觉系统，都带成文数值**：

| 系统 | 定位 | 主题（含实测色值） | 硬规则（原文） |
|---|---|---|---|
| **Style A** 电子杂志 × 电子墨水 | 叙事、观点、个人分享 | **5 套**：墨水经典 `#0a0a0b`/`#f1efea`、靛蓝瓷 `#0a1f3d`/`#f1f3f5`、森林墨 `#1a2e1f`/`#f5f1e8`、牛皮纸 `#2a1e13`/`#eedfc7`、沙丘 `#1f1a14`/`#f0e6d2` | 只换 `:root` 那几行主题色；**一份 deck 只用一套**；**不许混搭、不许用户自定义色值** |

- **它的定位不是课件**（原文"❌ 不合适：大段表格数据 / **培训课件（信息密度不够）** / 需要多人协作编辑"）⇒ 我们**不引入**它的 HTML deck 运行时，只借两块：**风格数值**与**校验思路**。

## 3. 数值：唯一权威（tokens）

### 3.1 文件与字段

`content/ppt_templates/_builtin/<主题>.json`（新建目录）：

```json
{
  "id": "tech-editorial",
  "name": "学术蓝",
  "source": "futuristic-tech-editorial-ppt-skill/references/style-system.md",
  "canvas":   { "w": 1280, "h": 720, "margin": 72, "content_w": [1040, 1120], "cols": 12, "gutter": 24, "bg": "#FFFFFF" },
  "palette":  { "text": "#2B2B2B", "accent": "#2F6BFF", "sub": "#6B6B6B", "line": "#E6EAF2", "soft": "#F7F9FC", "accent_max_ratio": 0.10 },
  "type":     { "cover": 72, "title": 44, "label": 12, "body": 24, "caption": 15,
                "lh_title": 1.08, "lh_body": 1.35, "para_gap_ratio": 0.6, "letter_spacing": 0 },
  "ranges":   { "cover": [56, 76], "title": [36, 48], "label": [11, 13], "body": [18, 24], "caption": [12, 15] },
  "weights":  { "cover": 700, "title": 700, "label": 600, "body": 400 },
  "fonts":    { "latin": "Arial", "ea": "微软雅黑", "stack": ["Arial", "微软雅黑", "sans-serif"] },
  "geometry": { "line_w": [1, 2], "radius": [0, 4], "shadow": false, "glow": false, "gradient": false, "texture": false },
  "density":  { "blocks_max": 5, "chars_per_block_max": 22 },
  "marker":   "accent",
  "derived":  {},
  "notes":    ["数值照抄上游 style-system.md，未改写"]
}
```

- `ranges` 是**上游给的字号区间**：`validate()` 会检查每个字号都落在自己的区间里（防止有人手改一个数就破坏阶梯）；
- `marker` 指"细小记号与标签用哪个颜色"（默认 `accent`；某套主题的 accent 太浅时指到 `accent2`，见插画暖）；
- `derived` 记录"上游没给、由主色与底色混合得到"的颜色，单测会核对它真的等于混合结果。

## 4. 渲染与坐标：固定画布 + 等比缩放

### 4.1 现在为什么会"比例会漂"

预览台是**固定 CSS px** 塞在**可拖宽**的容器里：`.dp-stage` 的 `padding:16px 18px`、`h4:17px`、`ul:12.5px`，而面板宽度可以是 320 / 680（默认）/ `min(1000px,80vw)`。

折算到 1280×720 画布（`scale = 容器宽 / 1280`，按默认 680 面板、内容宽约 648 计，scale ≈ 1.975）：

- 横向内边距 18px ⇒ **≈35.5 画布 px**（要求 ≥72px）；
- 页标题 17px ⇒ **≈33.6 画布 px**（要求 36–48px）；
- 正文 12.5px ⇒ **≈24.7 画布 px**（要求 18–24px，略超）。

面板一拖宽，同一份 CSS 折算出的画布 px 就变小 ⇒ **同一页在不同面板宽度下与导出的差距不同**，"预览 = 导出"永远不可能成立。这与"数值写在哪"无关，是坐标系问题。

### 4.2 做法（M1 已落地，2026-09-25）

1. **渲染收在服务端**（D13）：`POST /api/slide/render` 返回每页 SVG（`src/edu_agent/slide_deck.py` 调 `ppt_svg`），面板只负责显示——布局逻辑只有一份，不再有"前端拼 HTML"这条路；
2. 预览台内部固定 **1280×720**（`.dp-canvas`，SVG 原尺寸放进去）；
3. 外层 `.dp-slidewrap` 按宽度算 `scale = 宽 / 1280`（`slide_deck.fit_scale()`；面板里的 3 行 JS 是它的镜像，`panel_check.js` 断言 `data-scale` 与台子高度），用 `transform: scale(…)`（`transform-origin: top left`）**均匀**缩放，容器高度 = `720 × scale`；
4. 底色/字号/边距全部由 tokens 决定（SVG 内已写死显式颜色），面板 CSS 里**没有**幻灯片版式的字面量；旧的深蓝 `.dp-stage` 已删除；
5. 导出层用同一个常数把画布 px 换成 EMU（§3.3），所以"预览里 72px 的边距"和"pptx 里 54pt 的边距"是同一个东西；
6. 服务端渲染不可用时（接口失败/技能关闭）面板**退化成纯文本预览**并在状态行注明，不白屏。

### 4.3 验收

同一页在**面板宽 480 / 680 / 1000** 三种情况下，元素两两相对位置（归一化坐标）一致：因为只有一个均匀缩放，这是数学结论（`tests/test_slide_deck.py::FitScaleTest` 锁公式，`panel_check.js` 锁实际生效值）。与导出 pptx 的坐标一致性在 M3 的导出验收里比。

## 7. 质量闸门（四项指标）

### 7.1 定义（必须按公式算，否则是假精度）

> **2026-09-25 修正**：本节原来写的「空白率 = 1 − 文字并集面积 / 画布面积，目标 ≤45%」**算不出来也不可达**
> （文字墨迹本来就只占画布一小块，任何正常版式都会 >85%，那个 45% 是拍的）。
> 现在改成下面这套**可测且有意义**的定义，并已按 `docs/23` M2 实现、跑出真实基线（§7.2）。

| 指标 | 定义（实现见 `src/edu_agent/slide_audit.py`） | 为什么这么定义 |
|---|---|---|
| 宽高比合规 | 画布 `w/h` 与 `16/9` 的相对误差 ≤0.5%（我们固定 1280×720，天然为 0） | 变形是最刺眼的低级错误 |
| 安全边距合规 | 内容包围盒四边到画布边缘 ≥ `tokens.canvas.margin` | 直接对应"贴边"这个观感问题 |
| 内容纵向占比 | `(最低内容底 − 最高内容顶) ÷ 画布高 ≥ 74%`（**不是**按文字面积算空白） | 页面是不是"头重脚轻、下面一大片空"，这个数才说得清 [S11] |
| 底部空白 | `画布高 − 最低内容底 ≤ 170px` | 与上一条互补：一个看占比、一个看绝对留白 [S11] |
| 最大空白矩形 | 网格近似（64×64）+ 直方图法求最大空矩形占比 —— **只记录、不设卡** | 规范自己要求"一侧明显更安静" [S1]，一刀切会误杀；它的用途是"改版式前后别变糟" |
| 元素碰撞 | 文本盒子两两相交面积 > 1px² 才计；**只比文字与文字** | 幻灯片里文字压底色/压图是正常设计，不是 bug |
| 视觉失衡 | 以文字盒子的**面积**为质量：`abs(左 − 右) ÷ 总量 ≤ 12%`；**版式声明了"安静侧"时，落在安静侧方向的不判**（记 info） | 否则会和"留白"互相打架：左对齐版式天生左重 |
| 字号阶梯合规 | 每个 `<text>` 的 `font-size` 必须**正好**等于 tokens 的 5 档之一 | 防"随手加一个 13px 小字"把阶梯打散 |
| 主色占比 | 主色元素的**墨迹面积** ÷ 画布 < 10%。墨迹 = 矩形取面积、线/折线取 `长度 × 线宽`、文字取 `包围盒 × 0.5` | 用包围盒量曲线会把一条 2px 细线算成一大块色板（实测虚高到 11%，改成墨迹后 0.2%） |

**安静侧（`QUIET_SIDE`，定义在 `slide_audit.py`）**：`cover`→right、`bullets`→right、`end`→right、`media`→left、`section`→left、`two-col`→无（两侧都要平衡）。

### 7.1b 直接采纳的可测阈值（来自 [S11] 的校验脚本，D10）

上面四项是"好不好看"的宏观指标；下面这些是同一份脚本里已经跑通的"硬毛病"，**逐条照搬**（阈值可再调，定义先照抄）。
**实现状态**：已全部落进 `src/edu_agent/slide_audit.py`（`--gate` 时 error 非零退出），标注"我们版"的是按本项目的口径改写。

| 检查项 | 阈值 / 规则 | 判级 | 状态 |
|---|---|---|---|
| 版式白名单 | 只允许**已登记**的版式 id（我们：6 个）；出现未登记的版式即失败 | ❌ 错 | ✅ |
| 内容溢出 | 任何元素越出画布 > 0.5px（我们版：模型内量盒子，替代它的 DOM 溢出 4px） | ❌ 错 | ✅ |
| 内容安全线 | 内容不得越过画布 **93%** 高度线 | ⚠️ 警告 | ✅ |
| 底部空白 / 内容占比 | 底边空白 **>170px**、或内容纵向占比 **<74%** | ⚠️ 警告 | ✅ |
| 标题间距 | 大标题与其下一块 ≥**32px**；局部小标题 ≥**14px** | ⚠️ 警告 | ✅ |
| 标题对齐 | 标题不得居中（我们版：版式模板决定，`cover`/`section` 例外） | ❌ 错 | ✅（结构上保证） |

| 字号阶梯 | 字号必须取自 tokens 的 5 档 | ❌ 错 | ✅ |
| 报错措辞 | 每条错/警告都要给"**怎么修**"，且明确"**别删内容**" | 规范 | ✅ |
| 缺浏览器时 | 静态检查照跑；渲染测量降级为警告 —— **我们更进一步：完全不依赖浏览器** | 规范 | ✅ |

> 两条值得记住的取舍：① **能静态算的绝不靠浏览器**（jsdom 量不了几何、Edge `--dump-dom` 实测不可靠 ⇒ 改成模型内审计，见 §7.3）；② **闸门要教人怎么改，而不是只说不合格**，且不许把"删内容"当解法（与 §3.3"绝不截断"一致）。

### 7.2 基线（2026-09-25 **实测**）与目标

示例 deck = 封面 / 要点 / 图文三页；命令：`.venv\Scripts\python.exe tools\slide_audit.py`（`--json` 存原始数值到 `data/tmp/slide_audit/`）。

### 7.3 怎么量：**模型内几何审计**（不需要浏览器）

jsdom **没有排版引擎**：`getBoundingClientRect()` 恒为 0，几何一个都量不了（现有 `tools/uicheck/panel_check.js` 只做 DOM/行为检查，保留）。

本次把三条路都试过了（2026-09-25 实测）：

| 方案 | 结果 |
|---|---|
| jsdom 量几何 | ❌ 没有排版引擎，全 0 |
| Edge `--headless=new --dump-dom`（页内自测后抓 DOM） | ⚠️ **不可靠**：首次成功、之后稳定返回空（同样的命令同样的文件），不能作为验收依赖 |
| Edge `--headless=new --screenshot` | ✅ 稳定（样张 9 张 PNG 都是它出的），但只有像素、没有坐标 |

⇒ 结论：**审计不靠浏览器，改成"模型内"审计** ——

- 我们的渲染器自己知道每个元素的坐标（槽位 → SVG 是确定性生成），所以四项指标 + §7.1b 阈值**直接在 Python 里按同一套坐标算**：零依赖、确定性、可单测（含负样本）；
- 面板宽度只影响一个**均匀缩放**（`slide_deck.fit_scale()`），归一化坐标与缩放无关，所以"拖宽不变形"是数学结论，由 `panel_check.js` 断言缩放系数与台子高度；
- 浏览器仍然要用，但只用在**给人看**的地方：样张截图（`tools/slide_samples.py`）与 WPS 真机打开（M3）；
- 产出：审计报告写到控制台 + `data/tmp/slide_audit/<主题>.json`（原始数值），非零退出即验收失败。

## 10. 词汇表（非技术）

| 词 | 白话 |
|---|---|
| tokens（数值表） | 一张写着"字号多大、边距多宽、用什么颜色"的表；全项目只有一份 |
| 槽位（slot） | 一页里预留的位置，比如"标题放这儿、要点放这儿"；内容按位置填，不靠手摆 |
| SVG | 一种用文字描述图形的格式；浏览器能直接显示，也能被转换成 pptx |
| 原生可编辑 pptx | 下载出来的 pptx 里，文字就是普通文本框，能直接改字（不是一张图片） |
| 无头浏览器 | 没有窗口的浏览器，用来"在后台把网页画出来并量尺寸" |
| 基线 | 改造**之前**测到的数值；以后只要求"不比它差、并达到目标" |
| 母版 / 版式 | 幻灯片里预先定义好的页面样式；改母版会影响所有用它的页 |
