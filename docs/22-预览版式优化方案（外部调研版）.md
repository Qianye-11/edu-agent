## 0. 结论先行（三条路线，选哪条）

| 路线 | 做什么 | 出处 | 一期建议 |
|---|---|---|---|
| **A. 设计 tokens + 母版版式**（推荐先做） | 把我们自己的预览与导出都换成**一套规范化的 tokens**（画布/边距/12 栏网格/字号阶梯/配色占比）+ 用 **PptxGenJS 的 `defineSlideMaster`** 定义 6 个版式 | 版式规范：Awesome-PPT-Design-Skills 的 `style-system.md`；母版机制：PptxGenJS 官方 *Masters and Placeholders* | ✅ **一期** |
| **B. 预览即导出（HTML → 原生 pptx）** | 面板里那份 16:9 HTML 直接转成**可编辑 pptx**，预览与导出一份源 | `html-to-editable-pptx`（Claude Skill + Python CLI）；备选 `dom-to-pptx`（纯前端） | 二期（要先评估/装渲染器） |
| **C. 质量闸门（可验证指标）** | 用**四项可程序化验证的版式指标**卡住"难看"：宽高比失真 / 空白率 / 元素碰撞 / 视觉失衡 | 论文 **AeSlides**（arXiv 2604.22840）+ 其开源仓库 | ✅ **一期**（和 A 一起做） |

**一句话**：一期先把「规范 tokens + 母版版式 + 四项指标闸门」做掉 —— 这三样都是**确定性、可测**的，能直接解决"不好看"里最刺眼的部分；
"预览 = 导出"（路线 B）留二期，因为它的审计环节需要渲染器（见 §6）。

## 1. 现状为什么难看（对着规范逐条对差）

| 规范要求（出处 §7-①） | 我们现在的做法 | 差在哪 |
|---|---|---|
| 画布 16:9 `1280×720`、**安全边距 ≥72px**、内容宽 1040–1120px | `.dp-stage` 内边距 ~16px；导出 `pptx_native` 硬坐标 `Inches(0.6)` 起 | 边距不成体系，贴边、行宽不齐 |
| **12 栏网格 + 24px gutter** | 没有网格，全是"一行行往下排" | 元素左右不对齐，页面松散 |
| 字号阶梯（封面 56–76 / 页标题 36–48 / 正文 18–24 / 注释 12–15，行高 1.08 / 1.35–1.55） | 预览标题 17px、列表 12.5px（HTML 像素）；导出用 python-pptx 默认 44/32/20 | 层级不清、正文偏小；预览字号阶梯与导出**不一致** |
| 主色**占比 <10%**，其余走灰阶 | 整块深蓝底 + 白字（`.dp-stage` 是 `#0f172a` 满屏） | 满屏主色，像"开发调试页"而不是成品页 |
| **避免密集列点**，改成 labeled blocks / steps / timeline / comparison | 每页就是 `<h4>+<ul><li>` 列点 | 信息形态单一，这是"土味 PPT"的头号来源 |
| 页码 `x/N`、几何 1–2px 细线、圆角 0–4px、不用阴影/发光/3D | 无页码；卡片用 10px 圆角 + 阴影 | 装饰语言不统一 |

**另有两条硬伤**（不是规范问题，是工程问题）：

1. **预览与导出两套渲染**：面板是 HTML（`docpRenderSlides`），导出是 `pptxgenjs`（浏览器内存 deck）或服务端 `python-pptx`（`pptx_native`）——三处各写一套坐标，**"预览 = 将导出"从来没真正成立过**；
2. **中文字体错配**：导出主题里标题是 `Calibri`、中文落到 `宋体`（`docs/20` §3 的实测数据），是典型的"默认丑"组合。

## 2. 调研到的可用方案（每条都带出处）

### 2.1 版式规范：直接抄一份成熟的 design tokens

`Awesome-PPT-Design-Skills` 里的 [`style-system.md`](https://github.com/software-ai-life/Awesome-PPT-Design-Skills/blob/main/futuristic-tech-editorial-ppt-skill/references/style-system.md) 给了一整套**可直接落进代码的数值**：

- Canvas：16:9、`viewBox 0 0 1280 720`、背景 `#FFFFFF`、**安全边距 ≥72px**、内容宽 1040–1120px、**12 栏 + 24px gutter**；
- Palette：`#2B2B2B` 主文 / `#2F6BFF` 强调 / `#6B6B6B` 次文 / `#E6EAF2` 分隔线 / `#F7F9FC` 浅模块底，**强调色占比 <10%**；
- Typography：封面 56–76、页标题 36–48、节标签 11–13（大写）、正文 18–24、注释 12–15；行高 1.08（大标题）/ 1.35–1.55（正文）；**字距 0**；字体 `Inter / Arial / Microsoft YaHei`；
- Layout：**不对称**（一个主块 + 一个辅簇）、留白要"有一侧明显更安静"、用**细线做结构**而不是给每个元素套卡片、**优先开放模块而不是重卡片**、**避免密集列点 → 改成带标签的块 / 步骤 / 时间轴 / 对比模块**；
- Geometry：线宽 1–2px、圆角 0–4px、**不用软阴影/发光/模糊/径向渐变/3D**；
- 图表：扁平、克制，**蓝色只给要强调的那一条**，其它走石墨灰与浅网格。

> 这套规范是"某一风格"的（未来科技杂志风），但**结构**可以直接复用：我们的 3 套内置主题各写一份 tokens，字段完全一致（画布/网格/字号阶梯/配色/几何）。

### 2.2 母版机制：用 PptxGenJS 的 `defineSlideMaster`（我们已经在用这个库）

[PptxGenJS 官方 *Masters and Placeholders*](https://gitbrent.github.io/PptxGenJS/docs/masters/) 明确：

- `pptx.defineSlideMaster({ title, background, margin, objects, slideNumber })` 定义的母版，
  **在导出的 pptx 里就是真正的 Layout**（可在 WPS/PowerPoint 的"视图 → 幻灯片母版"里改，改动会影响用它的页）；
- 还支持**占位符**（`placeholder: { name, type: title|body|image|chart|table|media, x,y,w,h }`），
  之后 `slide.addText(text, { placeholder: 'body' })` 往槽里填 → 这正是我们 `docs/21` 想要的"槽"模型；
- 官方示例里连**页码**（`slideNumber: { x: 0.3, y: '90%' }`）都给了。

⚠️ **纠一个常见误解**：PptxGenJS 的 [HTML-to-PowerPoint](https://gitbrent.github.io/PptxGenJS/docs/html-to-powerpoint/) **只支持把 HTML `<table>` 转成 1~N 页**（`slide.tableToSlides()`），**不是通用 HTML→PPT**。所以路线 A 里"预览用 HTML、导出用 pptxgenjs"仍是两套渲染，得靠**共享 tokens**而不是共享 DOM 来对齐。

### 2.3 预览即导出（路线 B）：现成的 HTML → 原生可编辑 pptx

[`Hasasasa/html-to-editable-pptx`](https://github.com/Hasasasa/html-to-editable-pptx) 是一套"HTML 幻灯片 → 真正可编辑 pptx"的完整流水线（Claude Skill + Python CLI，`python convert.py deck.html`）：

- **矢量优先**：能用 PPT 原生 text / shape / line 表达的（背景色、边框、单边线、矩形椭圆）走原生；只有 OOXML 难表达的装饰（渐变/阴影/filter/混合模式/旋转裁切）才走**截图兜底**，且**文字永远保持矢量画在截图之上**；
- **字体**：HTML 用到的字体从 Google Fonts 拉取并 subset 嵌入；含中日韩字符自动种 `Noto Sans SC/Serif SC`；
  但注意它的实测结论：**PowerPoint COM 与 WPS 都不读 pptx 内嵌的裸 TTF** → 需要 `--install-user-fonts` 把字体装进系统字体目录，WPS 才会正确渲染；
- **两级自检**：Stage 5a 结构化自检（扫 OOXML 给提示）+ **Stage 5b 视觉 audit**（把 pptx 渲染成 PNG，与 HTML 半图对比，产出 `slide_NN_compare.png` 与 findings）；
- **修复纪律**：所有修复改 `<input>.audited.html`（源 HTML 不动），支持 `--only-slides 2,7,12` 增量重跑；
- 明确**不承诺 1:1 还原**（"OOXML 表达力有限"）。
- 备选：[`atharva9167j/dom-to-pptx`](https://github.com/atharva9167j/dom-to-pptx) —— **纯前端库**，把任意 DOM 元素转成可编辑 pptx（保渐变/阴影/圆角图/响应式）。好处是不用装服务端依赖、就在我们面板里跑；成熟度与许可需要先评估（**未核**）。

### 2.4 质量闸门：用"可验证指标"而不是"看着不错"

论文 [**AeSlides**（arXiv 2604.22840）](https://arxiv.org/abs/2604.22840) 的核心结论对我们很有用：

- 现在的做法（VLM 打分 / 反思 agent）**不可靠**：VLM 有系统性盲区（例如**测不出宽高比失真**）、与人类判断相关性弱、还容易被"刷分"，而且慢且贵；
- 它改用**四项可程序化验证的版式指标**：**宽高比失真、过量空白、元素碰撞、视觉失衡**；
- 实测增益：宽高比合规 **36% → 85%**、空白 **↓44%**、碰撞 **↓43%**、失衡 **↓28%**，人工评分 3.31 → 3.56；
- 它的[仓库](https://github.com/ympan0508/aeslides)因为商业限制**没开源完整系统**，但放出了核心片段：多奖励归一化、奖励塑形、**基于局部方差图的空白检测**、**基于 Playwright 的渲染逻辑**（可作为我们指标实现的参考）。

> 对我们的意义：**别用"模型觉得好不好看"当验收**；把上面四项指标算在我们自己的 16:9 DOM 上（面板已经渲染了每页，Playwright/jsdom 都能量），做成 CI 里的闸门。

### 2.5 明确不走的两条

| 方案 | 为什么不走 |
|---|---|
| **VLM 打分当验收** | AeSlides 已证伪：盲区 + 弱相关 + 易刷分 + 贵（同上） |
| **PptxGenJS `tableToSlides` 当通用 HTML→PPT** | 官方文档写明只处理 HTML 表格（同上） |

## 3. 推荐方案（一期做 A + C，二期做 B）

### 一期（确定性、可测、不依赖模型）

1. **落一份 tokens（单一事实源）**：`content/ppt_templates/_builtin/<主题>.json`，字段照 §2.1：
   `canvas{margin, cols, gutter, content_w}` / `type{cover,title,section,body,caption,lineHeight}` / `palette{bg,text,sub,accent,line,soft}` / `geometry{radius,lineWidth,noShadow:true}`；
2. **6 个版式**（沿用 `docs/21` 的定义）改成"**按 tokens 渲染**"：面板 HTML 与导出 pptxgenjs 都读同一份 tokens → 视觉一致；
3. **导出换成母版**：用 `defineSlideMaster` 定义 6 个版式（背景/边距/页码/装饰线在母版里），页面只往 placeholder 填内容
   → 老师拿到 pptx 后在"幻灯片母版"里一改，全篇跟着变（这是官方文档承诺的行为）；
4. **信息形态改造**（治"土味"的正招，出处 §2.1 Layout Rules）：把"一页 6 条列点"改成
   **带标签的块 / 步骤条 / 时间轴 / 左右对比**；每页要点 ≤4 条、每条 ≤18 字（超过给"拆页"提示，**不截断**）；
5. **字体**：中文统一 `微软雅黑`（或思源黑体）、西文 `Inter/Arial`，**字号阶梯按 tokens**；
   预览与导出一致；不引入需要嵌入的字体（WPS 不读内嵌裸 TTF，见 §2.3）；
6. **四项指标闸门**：新增 `tools/slide_audit.js`（Playwright 或 jsdom 量）：
   - 宽高比：所有页面容器 16:9（容差 ±0.5%）→ 必须 100%；
   - 空白率：内容包围盒外空白 ≤ tokens 上限（默认 45%）；
   - 元素碰撞：文本块两两重叠面积 = 0；
   - 视觉失衡：左右/上下质心偏移 ≤ 阈值（默认 12%）；
   接进 `tools/uicheck/panel_check.js` 与 `tools/ppt_acceptance.py`，**不达标就算验收失败**。

### 二期（预览即导出）

- 评估并接入 `html-to-editable-pptx`（或 `dom-to-pptx`），让"面板里那份 HTML"直接产出可编辑 pptx；
- 前置条件：**渲染器**。它的视觉 audit 需要 PowerPoint COM 或 LibreOffice；
  我们机器上**只有 WPS**（无 Office、无 LibreOffice）→ 要么装 LibreOffice（`winget install LibreOffice.LibreOffice`），
  要么用"WPS 另存为 PDF → 转 PNG"自建渲染器（WPS 有 COM 通道，但 `docs/08` 记过本机 WPS 演示 COM 是幽灵态）。

### 三期（可选）

- 让模型按场景（答辩/说课/汇报）**选版式 + 精简措辞 + 标图位**（这部分才需要强模型，成本与稳定性另算）。

## 5. 验收指标（一期目标值）

| 指标（出处 AeSlides） | 目标 | 怎么量 |
|---|---|---|
| 宽高比合规 | **100%**（容差 ±0.5%） | `slide_audit.js` 读每页容器尺寸 |
| 过量空白 | 空白率 ≤ **45%**（tokens 可调） | 内容包围盒 vs 画布 |
| 元素碰撞 | **0 处** | 文本块两两矩形相交检测 |
| 视觉失衡 | 质心偏移 ≤ **12%** | 左右/上下半区内容质量分布 |
| 字号阶梯合规 | 页标题/正文/注释**严格取自 tokens** | 渲染后读 computed style 比对 |
| 主色占比 | 强调色面积 **<10%** | 颜色面积统计（可选，二期） |

## 6. 风险与依赖

| 风险 | 说明 / 对策 |
|---|---|
| **字体在 WPS 里渲染不对** | `html-to-editable-pptx` 实测：**WPS 不读 pptx 内嵌裸 TTF**。对策：只用系统已装字体（微软雅黑/思源黑体），或走它的 `--install-user-fonts` 把字体装进用户字体目录（装之前会问） |
| **路线 B 的审计要渲染器** | 本机无 Office、无 LibreOffice（只有 WPS）→ 要么装 LibreOffice，要么先用一期指标闸门替代（**一期不依赖它**） |
| `dom-to-pptx` 成熟度未知 | 纯前端很诱人，但**我没核实它的维护状态与许可**；二期先做小样验证再定 |
| 版式改造会动现有导出 | `wps_export.pptx_native` 与 `docpBuildDeck` 都在用；改动要**保留旧路径可回退**（新增 `layout` 参数，默认走新母版，出问题一键切回） |
| 预览与导出仍是两套渲染 | 一期只能保证 **tokens 一致 + 版式一致**（不是像素一致）；真正"一份源"要等二期 |
